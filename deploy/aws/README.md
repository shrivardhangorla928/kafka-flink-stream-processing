# Deploying on AWS EKS

A short-lived demo cluster in ap-south-1. Two `t3.large` nodes, no NAT gateway, no load balancer.
It is a test cluster for the dissertation, not a production setup.

## What you need

- `aws` (configured with `aws configure`), `eksctl`, `kubectl`, Docker with buildx
- An IAM user that can create EKS, EC2, IAM roles, CloudFormation stacks and ECR repos

## Commands

| Script | What it does |
|---|---|
| `up.sh` | Creates the ECR repos, builds and pushes the images, creates the cluster, applies `overlays/eks`, waits for every workload, then runs `cicd-up.sh` and `expose.sh`. Safe to run again. |
| `cicd-up.sh` | Puts SonarQube and Jenkins in the `cicd` namespace on the same nodes. Builds and pushes the Jenkins image, gives Jenkins an IAM role for ECR, creates the Sonar project, token and webhook. |
| `expose.sh` | Creates a public load balancer for Grafana, Prometheus, the Flink UI, Jenkins and SonarQube, open only to your current IP. Run it again if your IP changes (`MY_IP=1.2.3.4` overrides the detected one). |
| `verify.sh` | Port-forwards the services, checks health and the Flink job, posts a 250 mm reading and waits for the EXTREME alert. |
| `down.sh` | Deletes the namespace, the cluster and the ECR repos, then lists anything left that could bill. `--keep-images` keeps the repos. |

The images are tagged `eks-<git short sha>`. A rerun on the same commit skips the build.

## Reaching the services

`expose.sh` prints the addresses. They are plain HTTP on classic load balancers, and the security group only allows your IP.
Logins are generated by `up.sh` into `deploy/aws/.secrets.env` (gitignored): Grafana admin, Jenkins admin and SonarQube admin.

Without the load balancers, use port-forward:

```
kubectl -n stream port-forward svc/grafana 3000:3000
kubectl -n stream port-forward svc/prometheus 9090:9090
kubectl -n stream port-forward svc/flink-jobmanager 8081:8081
```

## Jenkins and SonarQube on the cluster

They run in the `cicd` namespace, which allows privileged pods because the Jenkins pod has a Docker daemon sidecar for the image builds.
The `jenkins` service account has an IAM role that can push to ECR and is bound to `cluster-admin`, which is only acceptable on a short-lived demo cluster.
The job `stream-processing` builds branch `develop` using `Jenkinsfile.eks`, so the commit has to be pushed before Jenkins can see it.
SonarQube runs with `SONAR_VALIDATEWEBHOOKS=false`, because it refuses to call Jenkins on a private cluster address otherwise and the quality gate step then waits until it times out.
The first build needs `SKIP_QUALITY_GATE=true`. Run `deploy/cicd/sonarqube/quality-gate.sh` after it (set `ENV_FILE` and `SONAR_URL` as `cicd-up.sh` does), then build again with the gate on.

## The eks overlay

`deploy/k8s/overlays/eks` sits on top of the `aws` overlay and changes four things:

- Images come from ECR (`up.sh` fills in the registry and tag).
- A `gp3` default StorageClass on the EBS CSI driver. This EKS version has no default class, so every PVC stayed Pending.
- `flink-state` is ReadWriteOnce, and the TaskManager is pinned to the JobManager's node. EBS cannot be ReadWriteMany.
- Kafka writes to `/var/lib/kafka/data/logs`. An ext4 volume has `lost+found` at its root and Kafka refuses to start with it.

Two fixes went into the `aws` overlay itself, because it had never been run before:

- JobManager memory 600m to 768m (limit 1Gi). At 600m the heap was 24 MB and it ran out of memory.
- TaskManager memory 700m to 1024m (limit 1280Mi). At 700m Flink rejects the memory sizes.
- `PARALLELISM=1` on the JobManager. The job reads its own parallelism and ignored `parallelism.default`, so it asked for 3 slots on a 1-slot cluster.

## Cost

About 25 INR per hour for the cluster (control plane, two nodes, disks, public IPs) plus about 3 INR per hour for each of the five load balancers, at 88 INR per USD. The control plane cannot be stopped. Delete the cluster when you are not using it.
